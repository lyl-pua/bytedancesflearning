## 一、大模型到底是什么

一句话：**一个根据前文预测下一个 token 的概率模型**。

你给它一段文字（输入 = prompt），它一个字一个字往后「接」，接到它认为该停为止。
它没有记忆、没有联网、不会算数（除非工具帮它算）——它的全部能力都体现在「接得准不准」。

### 1.1 Token（词元）

- **token 是计费和长度的最小单位**，不是「一个字」。
- 英文大约 4 个字符 ≈ 1 token；中文大约 1 个字 ≈ 1~2 token。
- 价格、速度、上下文长度，全部按 token 算。
- 在代码里能看到的地方：
  - `config.yaml` 的 `max_tokens: 8192`（这一次回答最多生成 8192 个 token）
  - `config.yaml` 的 `context_window: 131072`（这次对话总共能塞进 13 万 token）
  - 接口返回的 `response_metadata.token_usage`（`prompt_tokens` 输入 / `completion_tokens` 输出）

> 你之前问过「为什么 token 消耗这么快」——根本原因就是：**每一轮对话都要把历史全部重新发一遍**。
> 这就是下面要讲的「上下文窗口」的副作用。

### 1.2 上下文窗口（context window）

模型一次能「看见」的 token 上限。超了就两种下场：
1. 报错；
2. 系统自动把老消息删掉/压缩（本项目叫 **context compaction / summarization**）。

所以一个对话聊很久之后，模型会「忘事」——不是它变笨，是**老内容被挤出去了**。

### 1.3 Prompt（提示词）

发给模型的全部文本。分三层：

| 层 | 谁写的 | 本项目位置 |
|---|---|---|
| **system prompt**（系统提示） | 开发者写死，定义「你是谁、能干什么」 | `agents/lead_agent/prompt.py` |
| **user message**（用户消息） | 用户输入 | 前端输入框 |
| **assistant message**（模型回复） | 模型生成 | 接口返回 |
| **tool message**（工具结果） | 程序填，把工具返回喂回模型 | `tools/` 各工具 |

代码里就是一个数组：

```python
[{"role": "system",    "content": "你是 DeerFlow..."},
 {"role": "user",      "content": "介绍一下你自己"},
 {"role": "assistant", "content": None, "tool_calls": [...]},   # 模型要求调工具
 {"role": "tool",      "content": "搜索结果...", "tool_call_id": "..."}]
```

> **知识锚点**：`agents/lead_agent/prompt.py` 里能看到这个项目「人设」是怎么一句句写出来的，
> 包括它规定 Agent 什么时候该问澄清、什么时候该直接干。

## 二、Function Calling：模型怎么「用工具」

模型本身不能执行代码。所谓「Agent 会搜索、会写文件」，机制是：

```
1. 你把「有哪些工具 + 每个工具的参数说明」一起发给模型（这些也占 token！）
2. 模型不直接回答，而是回一个「我要调用 search(query="xxx")」的结构化指令（tool_calls）
3. 你的程序真的去执行这个工具，把结果作为 tool 消息再发回模型
4. 模型看到结果，继续生成，或者再要下一个工具
```

这就是 **Agent 的核心循环**：`想 → 调工具 → 看结果 → 再想`，直到它认为可以收尾。

本项目对应位置：
- 工具的定义与清单：`packages/harness/deerflow/tools/tools.py` 的 `get_available_tools()`
- 工具实际执行 & 隔离：`packages/harness/deerflow/sandbox/`
- 模型侧的适配：`models/patched_deepseek.py`（不同厂商返回的 `tool_calls` 格式略有差异，需要抹平）

> 注意：**工具描述本身也要消耗 token**。工具开得越多，每一轮的固定开销越大。
> 这也是「插件太多会很贵」的原因之一。

## 三、LangChain 与 LangGraph

### 3.1 LangChain：一层「各家大模型统一接口」

DeepSeek、OpenAI、Claude 的 HTTP 接口细节都不一样。LangChain 用一个统一的
`BaseChatModel` 抽象把它们包起来，你只写 `model.invoke(messages)`，换厂商只换实现类。

本项目：`models/factory.py` 的 `create_chat_model()` 就是干这个——
读 `config.yaml` 的 `use:` 字段，动态 import 出适配器类，造一个统一的 chat model。

```
config.yaml
  models[0].use = "deerflow.models.patched_deepseek:PatchedChatDeepSeek"
                       │                    │
                    模块路径            类名
        ↓ importlib 动态导入
   PatchedChatDeepSeek(...)  →  一个标准的 LangChain 聊天模型对象
```

> 这是典型的**工厂模式 + 配置驱动**：加一个新模型，只用改 yaml，不动代码。

### 3.2 LangGraph：把「多步流程」画成一张图

普通 Agent 是一段 while 循环。一旦要加「先规划、再执行、再反思、再总结」，
用 if/else 写会变成一坨面条。LangGraph 让你把它写成**图**：

| 概念 | 类比 | 本项目 |
|---|---|---|
| **State**（状态） | 一个共享的白板，所有节点在上面读写 | `agents/thread_state.py` |
| **Node**（节点） | 一个函数：读白板 → 干活 → 写回白板 | `lead_agent/agent.py` |
| **Edge**（边） | 下一步去哪；可以是条件边 | 同上 |
| **StateGraph** | 整张图的容器 | 同上 |
| **Checkpointer**（检查点） | 每走一步就把白板拍照存档，可断点续跑 | `runtime/checkpointer/` |
| **thread_id** | 存档的「档案号」，同一档案号=同一段对话 | 前端传的 thread_id |

**为什么需要 Checkpointer？**
1. 对话可以延续（下次调用接着上次的白板）；
2. 程序崩了能恢复；
3. 用户在生成中途点「停止」，也能从上一个检查点回滚。

代码里 `langgraph.json` 就是「这张图的登记表」：

```json
{ "graphs": { "lead_agent": "deerflow.agents:make_lead_agent" } }
```
意思是：图的工厂函数是 `deerflow.agents` 里的 `make_lead_agent`。

### 3.3 State 的 reducer

状态里 `messages` 是「一直追加」的列表，而不是每次覆盖。
LangGraph 用 **reducer**（默认 `add_messages`）描述「新值怎么合并进旧值」。
看到 `Annotated[list, add_messages]` 这种写法就是它——本项目的 `thread_state.py` 里就有。

## 四、中间件（Middleware）：Agent 的「流水线改装配件」

一个请求进入图之前/之后，可以插入一连串处理函数，这就是中间件链。
本项目的 `agents/middlewares/` 里能看到很多：

| 中间件 | 干什么 | 类比 |
|---|---|---|
| summarization | 上下文太长时，把老消息压成摘要 | 会议纪要 |
| dynamic context | 每天注入「今天是几号」这类实时信息 | 日历提醒 |
| 任务清单 / todo | 让 Agent 维护待办 | 便利贴 |
| 沙箱 | 把工具执行放进隔离环境 | 虚拟机 |

> 为什么叫「上下文工程」：模型只能看到你给它的 token，**给它什么，它就像什么**。
> 中间件就是在「喂给模型之前」做加工的那一层。

## 五、流式输出（SSE）

如果等模型全部想完再一次性返回，用户会盯着空白屏幕十几秒。
**SSE（Server-Sent Events）** 是一种「服务器不断往浏览器推小段数据」的 HTTP 技术：

```
HTTP/1.1 200 OK
Content-Type: text/event-stream

event: messages
data: {"content": "我"}

event: messages
data: {"content": "是"}

event: end
data: {}
```

浏览器收到一段就渲染一段，于是有了「打字机效果」。

本项目链路：
```
LangGraph 图执行 → 产生事件
   ↓ runtime/stream_bridge（内存事件总线，按 run_id 分发）
thread_runs.py 的 sse_consumer 把事件转成 SSE 文本
   ↓ HTTP
前端 use-thread-chat.ts 消费事件 → stream-state.ts 合并成消息列表 → 渲染
```

> 知识点：`on_disconnect` 参数（默认 `cancel`）= 用户关页面就取消这次运行，省钱。

## 六、记忆（Memory）

上下文窗口是**短期记忆**（关掉就没了）。「长期记忆」要另外存：

| 类型 | 存什么 | 本项目 |
|---|---|---|
| 短期 | 当前对话的消息 | checkpointer（SQLite / Postgres） |
| 长期 | 用户的偏好、事实、结论 | `agents/memory/`（deermem / mem0 / honcho 多后端） |

实现思路（也就是常说的 **RAG 精神**）：写入时抽取要点存成条目；需要时按相关性检索，
把最相关的几条塞回 system prompt。区别是 RAG 通常检索「文档」，记忆检索「关于你的事」。

代码入口：`agents/memory/manager.py`。

## 七、沙箱（Sandbox）

Agent 会执行命令、写文件。直接在你电脑上跑 = 危险（`rm -rf` 也不是不可能）。
沙箱就是给它一个「笼子」：

- 限制可访问的目录（防路径穿越 `../../etc/passwd`）
- 禁止执行宿主机 shell（本项目的 `allow_host_bash: false`）
- 限制网络、超时、资源

本项目的实现是可替换的：`config.yaml` 的 `sandbox.use: deerflow.sandbox.local:LocalSandboxProvider`
表示「本机执行版」，生产上可以换成容器/远程沙箱实现，**接口不变**。

## 八、认证：JWT、Cookie、CSRF

这块是你本次踩坑最多的地方，值得单独讲清楚。

### 8.1 JWT

登录成功后，后端发一个**签名过的字符串**（token），里面写着「我是谁、什么时候过期」。
后端不存 session，只验签名 —— 这就是 JWT（JSON Web Token）。

本项目的 `access_token` Cookie 就是 JWT，`HttpOnly` 表示 **JS 读不到它**（防 XSS 偷 token）。

### 8.2 Cookie 与 SameSite

- `HttpOnly`：JS 读不到
- `SameSite=lax`：跨站请求默认不带这个 Cookie（防 CSRF 的第一道墙）
- `Max-Age=604800`：7 天（即「记住我」）

### 8.3 CSRF（跨站请求伪造）

攻击场景：你登录了银行，然后访问了恶意网站，那个网站偷偷向银行发「转账」请求——
浏览器会自动带上你的 Cookie，银行以为是你本人。

防御（**双提交 Cookie**）：后端给前端一个 `csrf_token` Cookie（这个 **允许 JS 读**），
前端每次 POST 都要把它放进 `X-CSRF-Token` 请求头。攻击者的站点读不到你的 Cookie，也就伪造不出来。
后端比对「头里的值」和「Cookie 里的值」是否一致。

代码：`backend/app/gateway/csrf_middleware.py`。

### 8.4 首启动的「初始化」流程

```
GET /api/v1/auth/setup-status  → {"needs_setup": true}
     ↓ 前端把用户导到 /setup
POST /api/v1/auth/initialize  {email, password}
     ↓ 只在「还没有管理员」时允许，否则 409
返回 201 + Set-Cookie(access_token)
```

> 本机踩的坑：`email` 用 pydantic 的 `EmailStr` 校验，**`.test`/`.local` 是保留域名会被拒（422）**，
> 而前端没弹错误提示，看起来像「点了没反应」。这就是「错误必须显示出来」的经典案例。

## 九、前端：从「事件流」到「界面」

React 里做流式聊天，核心是三件事：

1. **发起请求**（`fetch` 或 SDK 的 `useStream`）
2. **增量合并状态**：每来一个事件，就更新消息列表（不能整表重渲染，否则卡）
3. **滚动跟随**：只有用户停在底部时才自动滚（`use-stick-to-bottom`）

本项目：
- `components/workspace/chats/use-thread-chat.ts` —— 发起 + 订阅
- `core/threads/stream-state.ts` —— 把事件合并成 UI 状态（纯函数，好测试）
- `components/workspace/chats/chat-box.tsx` —— 输入框 & 发送按钮

> 一个常见误区：以为前端在「直接调 DeepSeek」。
> 其实前端只跟 **Gateway** 说话，模型密钥永远在服务端 —— 这是**所有** AI 应用的铁律。

## 十、为什么 Agent 项目会「很贵」—— 三个固定开销

1. **历史重发**：每一轮都把之前的全部消息再发一次 → 成本随轮数**平方级**增长。
2. **工具描述**：每个工具的 JSON Schema 都要塞进 prompt，工具越多越贵。
3. **系统提示词**：Agent 的「人设 + 规则」往往几千 token，每轮都带。

省钱手段（本项目都实现了）：
- **上下文压缩**：`runtime/context_compaction.py` + `summarization_middleware`
- **缓存命中**：DeepSeek 的 `prompt_cache_hit_tokens`（相同前缀可复用）
- **按需加载技能**：`skills/` 只在需要时才把说明书塞进上下文（渐进式披露）
- **及时结束**：`on_disconnect=cancel`

## 十一、术语速查表

| 词 | 一句话解释 |
|---|---|
| LLM | 大语言模型，预测下一个 token |
| Token | 计费单位，约等于「小半个词」 |
| Prompt | 发给模型的全部文本 |
| System prompt | 开发者预设的角色设定 |
| Context window | 一次能看见的 token 上限 |
| Temperature | 随机性（越低越稳定） |
| Function calling | 模型要求程序去执行某个函数 |
| Tool / Skill | 模型可调用的能力；Skill 更偏「说明书 + 脚本包」 |
| Agent | LLM + 工具 + 循环 + 记忆 |
| LangChain | 各家模型的统一封装 |
| LangGraph | 把 Agent 流程画成状态图 |
| Checkpointer | 每步存档，支持续跑 |
| thread_id | 存档档案号 = 一段对话 |
| SSE | 服务器持续推送小段数据的技术 |
| RAG | 先检索再生成 |
| Reranker | 检索结果再排序 |

| CSRF token | 双提交 Cookie 防御用的随机串 |

## 十二、下一步学什么（按性价比排序）

1. **把 `prompt.py` 改一句话**，重启，感受系统提示词对行为的影响 —— 这是最便宜的学习方式。
2. **加一个自己的工具**（比如查天气），注册到 `tools.py`，看模型怎么选它。
3. **打开 `supports_thinking`**，对比 `reasoning_content` 有无，理解「思维链」。
4. **故意把上下文塞爆**，观察 summarization 中间件怎么压缩 —— 理解 token 预算。
5. 再去看 `docs/ARCHITECTURE.md`（官方英文架构文档），这时候你应该能读懂大半了。
